CWIST

C Web development Is Still Trustworthy

Write a web app once in C. Serve it from a native server, from a WASI 0.2 edge runtime, or from inside the browser's Service Worker.

CWIST is a C17 web framework and application server: routing, middleware, templates, sessions, validation and an embedded SQLite ORM on top of HTTP/1.1, HTTP/2, HTTP/3, WebSocket and WebTransport, with an io_uring/epoll/kqueue reactor.

Powered by CWIST in production: oborona.zip (daily engineering blog) · fly.board

Quick start

brew tap c4punks/cwist
brew install c4punks/cwist/cwist
#include <cwist/app.h>
static void hello(cwist_http_request *req, cwist_http_response *res) {
(void)req;
cwist_sstring_assign(res->body, "Hello from CWIST!");
}
int main(void) {
cwist_app *app = cwist_app_create();
cwist_app_get(app, "/", hello);
cwist_app_listen(app, 8080);
cwist_app_destroy(app);
return 0;
}

One app, three places to run it

A CWIST app is a set of routes on a cwist_app. Where it runs depends only on how you hand that app to a host:

Host Entry point What you get Example
Native server (Linux, macOS, BSD) cwist_app_listen(app, port) The full stack: HTTP/1.1–3, TLS, WebSocket, WebTransport, C1M reactor simple-server
Browser Service Worker CWIST_WASM_DEFINE_ENTRY(app), built with emcc Routing, zod validation, templates, cwist_db and signed-cookie sessions answering fetch inside the browser: no origin server, no framework JS wasm-service-worker
WASI 0.2 edge runtime (Wasmtime) cwist_app_listen on WASI sockets, built for wasm32-wasip2 The same app on Wasmtime; the host owns persistence as a KV-style blob wasip2-kv

The WASM hosts speak serialized HTTP/1.1 across a WIT interface, and the cwist-wasm npm package wraps the jco-transpiled component for JavaScript hosts. They are newer than the native server: read each example's README for what is and is not guaranteed yet (for example, the wasip2 demo does not promise crash-durable writes).

Two server modes

The mode is one environment variable; pick per workload.

  • CWIST reactor (default, CWIST_C1M_MODE unset or 1) takes throughput and connection density. Many connections share each event loop, so a held connection costs a reactor slot (about 5 KB over TLS) instead of a parked thread. Start here for APIs, web pages, webhooks, SSE fan-out, WebSocket chat and anything that holds many mostly idle connections.
  • CWIST Classic pool (CWIST_C1M_MODE=0) takes median latency. Each connection gets its own thread, so no request waits behind another in a batch. Pick it for short request bursts where the median matters more than connection count; it cannot reach C1M, because a million threads exceeds threads-max.

Holding a million connections

Measured on one 12-core machine (Ryzen 5 5600X, 62 GB, Linux 6.12, loopback):

Run Result Server memory
C1M cleartext, reactor, 12 workers (2026-09-29) 1,000,000 / 1,000,000 responded ~22.9 GiB peak RSS (~24 KB per connection)
C100K HTTPS, reactor, 4 workers (2026-10-17) 100,000 / 100,000 established, 0 dropped, all answered 4,975 B per open connection
C1M HTTPS, reactor (2026-10-18) 1,000,000 / 1,000,000 established, 0 dropped, all answered 4.56 GiB above idle (4,866 B per open connection)
C1M over TLS HTTP/1.1 and HTTP/2 via fly.board 1,000,000 / 1,000,000 held and served, zero failures 19.9 GB / 30.1 GB PSS

The HTTPS ramp is handshake-bound (~2,900 full P-256 handshakes/s, so ~340 s to open 1M connections). Kernel prerequisites, the client tooling fixes the runs needed, and the per-run details are in docs/performance/https-c100k.md and docs/c1m-file-limits.md.

Known limits of the async path: HTTPS still runs the request phase on pool threads, a handler that writes faster than the socket drains waits inside the reactor thread (bounded by CWIST_HTTP_TIMEOUT_MS), and idle cleartext keep-alive connections are not yet reaped by a timer.

Why C, when Axum and Gin exist?

  1. Your C and C++ code is already the backend. Libraries for finance, game servers, ML inference or device control link straight into the server with no FFI layer, no serialization boundary and no second runtime.
  2. The same app reaches the browser and the edge. C compiles to WASM with mature toolchains, which is what lets one CWIST app run in all three hosts above.
  3. Predictable footprint and start-up. No garbage collector, VM or JIT warm-up: the reactor's RSS is above the Rust frameworks but below Go and about 60× below the JVM.
  4. Competitive throughput and median latency, with the tail trade-off stated in the table above rather than hidden.

Memory safety and security in C

The first question about a C web server is buffer overflows, use-after-free and leaks. What CWIST does about it, and where each check lives:

  • Sanitizers on every push and PR. The test suite, tutorials and examples build with SANITIZE=address,undefined WERROR=1 and run under ASan/UBSan (asan.yml); ThreadSanitizer, CodeQL and cppcheck run in their own workflows.
  • Protocol conformance. An h2spec HTTP/2 run is diffed against a pinned baseline (scripts/ci/h2spec-baseline.txt); regressions fail the build.
  • Allocator gate. New raw malloc/free calls in the framework fail cwist audit --gate against scripts/ci/malloc-baseline.txt (malloc_lint.sh).
  • Fuzzing. A libFuzzer target covers the sequenced-chunk assembler (make fuzz_seq, tests/fuzz_seq.c). Fuzz targets for the HTTP/1.1, HTTP/2, WebSocket and multipart parsers are not written yet, and contributions are welcome.
  • Deterministic lifetimes. Request buffers and cached replies live in libttak generational arenas and epoch-based reclamation critical sections. Deferred responses use an explicit ownership handoff, and CWIST_ASYNC_STRICT=1 turns misuse into an abort instead of a warning.
  • Secure defaults. Hybrid post-quantum TLS with TLS 1.3 minimum, a built-in WAF, token-bucket rate limiting, timing-safe HMAC session verification, CSRF tokens and strict security headers (HSTS, COOP, Permissions-Policy).

Design decisions and their current status are recorded in docs/decisions/.

Install

CWIST vendors its dependencies (BoringSSL, lsquic, libttak, SQLite3), so a plain build works on a fresh Linux, macOS, or BSD machine:

git clone https://github.com/c4punks/CWIST.git
cd cwist
make
sudo make install # optional, installs to /usr/local (override with PREFIX=/opt/cwist)

Homebrew

macOS and Linux (Linuxbrew) users can install the latest release from the CWIST tap:

brew tap c4punks/cwist
brew install cwist

The formula builds from the release source tarball (dist/cwist-<version>.tar.gz, vendored dependencies included) and installs libcwist.a, public headers, the cwist CLI, and cwist.pc pkg-config metadata under the Homebrew prefix.

Platform support

CWIST builds on Linux, macOS, and BSD. On Linux the reactor uses io_uring (raw syscalls, no liburing) and falls back to epoll if ring setup fails; macOS and BSD use kqueue. The HTTP/3 server and native client use non-blocking UDP sockets on every platform, and ECN metadata is enabled only when the host exposes the required socket options. Reactor internals (one-shot polls vs completion-staged receives, CWIST_RX_URING, latency probes) are described in docs/http-reactor-fairness.md and docs/runtime-config.md.

The cwist CLI and hot reload

make install also installs the cwist command line tool into $(PREFIX)/bin.

# Scaffold a project: src/main.c, Makefile, and a demo.cwpro manifest
cwist new project demo --directory ~/src
cd ~/src/demo
# Develop with hot reload (incremental rebuild + zero-downtime restart)
cwist watcher
# Generate OpenAPI 3.1 from Doxygen @openapi.* route annotations
cwist openapi
# Generate C models and gRPC method paths from proto3 definitions
cwist proto api.proto
# Inspect the project manifest and detected routes
cwist describe

The watcher rebuilds only the affected translation units and restarts the app only after a successful build, so the previous process keeps serving if a build fails. It wakes on inotify (Linux) or kqueue (BSD/macOS) with a polling fallback; --no-run rebuilds without running and --poll forces polling. The .cwpro manifest (cwist-project/v1) holds the entry point, include paths, debounce/stop timeouts and route discovery scope for the watcher and generators.

Linking

libcwist.a is a thin static archive: it contains only CWIST objects. make install installs the vendored libraries under $(PREFIX)/lib/cwist and their headers under $(PREFIX)/include/cwist/vendor. pkg-config resolves all of it:

gcc -o server main.c $(pkg-config --cflags --libs cwist)
# fully static:
gcc -o server main.c $(pkg-config --cflags --libs --static cwist)

Without pkg-config, link CWIST first and its dependencies after it:

gcc -I/opt/cwist/include -I/opt/cwist/include/cwist/vendor main.c \
-L/opt/cwist/lib -L/opt/cwist/lib/cwist -lcwist \
-llsquic -lssl -lcrypto -lnats_static -lttak -lcjson -luriparser \
-lz -lzstd -lbrotlienc -lbrotlicommon -ldl -lpthread -lm -lstdc++

-lnghttp2 (HTTP/2) and -lcurl (RDBMS auto-mount probing) are optional. Brotli ships as libbrotli-dev on Debian/Ubuntu and brotli-devel on Fedora/RHEL; zstd as libzstd-dev / libzstd-devel. DESTDIR is supported for staged packages.

Feature notes

PQC TLS. cwist_app_use_pqc_layer(app, true) forces X25519MLKEM768:X25519:P-256, sets TLS 1.3 as the minimum and strips legacy ciphers. Application code never touches OpenSSL directly.

WebTransport. cwist_app_use_webtransport(app, handler) handles the CONNECT negotiation over HTTP/3 and exposes cwist_webtransport_read/write/flush/close/open_bidi/open_uni.

Nuke DB. cwist_nuke_init("data.db", 5000) loads an on-disk SQLite file into memory with sqlite3_deserialize, runs PRAGMA integrity_check, serves every query from RAM and syncs to disk on COMMIT. If bootstrap fails, it falls back to read-only disk protection mode.

RDBMS auto-mount. cwist_app_auto_rdbms(app, 5432) classifies the server by wire protocol (a PostgreSQL StartupMessage or a MySQL handshake packet) instead of guessing from the port number.

libttak. The in-tree allocator/reactor toolkit provides generational arenas, epoch-based reclamation, signal-safe detachable arenas for TLS and WebSocket buffers, and a lock-free job queue.
