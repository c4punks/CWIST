Detailed Description

Serve a CWIST app over lwIP's raw TCP API (issue #447 Phase 3).

For targets without BSD sockets (bare metal, or an RTOS running lwIP in NO_SYS / tcpip-thread mode): the adapter owns a listening tcp_pcb, frames HTTP/1.1 requests out of the received pbufs, runs them through the app's router and middleware (cwist_app_dispatch), and streams the serialized response back with tcp_write/tcp_sent back-pressure.

Build: compile src/sys/port/lwip.c into the firmware next to lwIP, with the firmware's lwipopts.h on the include path (the adapter depends on its TCP options). It needs LWIP_TCP and LWIP_CALLBACK_API, and uses only the raw API, so it works under NO_SYS=1. With SO_REUSE=1 the listener sets SOF_REUSEADDR, so it can be re-created while closed connections sit in TIME_WAIT.

Context: every call here, and every callback the adapter installs, runs in lwIP's core context: the main loop for NO_SYS=1, the tcpip thread otherwise (wrap calls in tcpip_callback()). Handlers therefore run there too; keep them short.

Behaviour:

  • Request bodies are framed by Content-Length. Transfer-Encoding is answered with 501, Content-Length together with Transfer-Encoding or an invalid/conflicting Content-Length with 400, an oversized header block with 431 and an oversized body with 413; the connection then closes.
  • Expect: 100-continue gets an interim 100 before the body is read.
  • Keep-alive follows the request and the response (as on the socket path); pipelined requests are answered in order, one at a time.
  • Responses are sent zero-copy from the serialized buffer, which is released once the peer has acknowledged it.
  • Received data beyond the request limits is refused back to lwIP while a response is in flight, so the TCP window throttles the peer.
  • Connections idle longer than idle_timeout_ms, or beyond max_conns at accept time, are closed (the latter aborted).
  • Deferred (cwist_async) and upgraded (WebSocket) responses are not supported here.
