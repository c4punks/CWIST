C1M 리액터 묶음 비우기에서의 협력적 큐잉 (이슈 #25)

상태: 구현됨, 기본으로 켜짐 (CWIST_REACTOR_DRAIN_CHUNK, src/sys/io/reactor.c). 변수가 설정되지 않았을 때 리액터의 내장 대체값은 64이지만, cwist_apply_profile()(기본값을 포함한 모든 CWIST_PROFILE에 대해 cwist_app_listen()이 호출)이 이를 8로 설정하므로 앱 수준 기본값은 더 촘촘한 청크를 씁니다. 기존 동작(묶음 중간의 비우기 없음)으로 되돌리려면 0으로 설정하세요. 이 캐던스는 모든 백엔드에 적용됩니다. io_uring CQE 묶음, epoll 이벤트 배열 (epoll_wait당 최대 1024개), kqueue 이벤트 배열.

배경

이슈 #25는 CWIST의 P99.999 꼬리 지연 시간을 추적합니다. 이미 두 차례의 실제 수정이 반영되었습니다 (이슈 스레드 참고). 하나는 yield-batch 수정(ce970136, 연결 하나가 한 턴에 인라인으로 처리하는 파이프라인 요청 수를 제한)이고, 다른 하나는 응답 병합(0bcc4f5a)입니다. 둘 다 **연결 내부**의 head-of-line 블로킹, 즉 한 연결의 파이프라인 적체가 리액터를 독점하는 문제를 겨냥합니다.

이 수정은 지금까지 다루지 않았던 다른 계층을 겨냥합니다. 하나의 리액터 깨우기 라운드 안에서의 연결 간 순서입니다. io_uring 분기에서 발견되어 먼저 수정되었고, epoll과 kqueue 루프도 똑같은 모양(라운드 맨 위의 비우기 한 번, 그 뒤 이벤트 배열 전체를 아무것도 끼워 넣지 않고 실행)이었으므로 같은 캐던스를 갖습니다.

빈틈

cwist_reactor_run()의 io_uring 분기는 깨어날 때마다 CQE 묶음 전체를 동기적으로 비웁니다.

while (head != tail) {
ev_ctx->cb(ev_ctx->fd, ev_ctx->ctx); /* runs the connection's handler inline */
head++;
}
queue_deferred(reactor); /* re-arms accumulated during this round */

링의 깊이는 4096 항목이므로, 준비된 연결이 몰리면(부하 급증, 또는 같은 라운드에 많은 소켓이 읽기 가능해질 만큼의 동시성) 한 묶음에 연결 수백 개가 들어갈 수 있습니다. 각 연결은 다음 연결이 시작하기도 전에 인라인으로, 동기적으로, 끝까지 처리됩니다.

별개로, cwist_reactor_post()는 외부 스레드(cwist_async_defer를 통한 백그라운드 DB/작업 완료)가 끝난 continuation을 리액터의 소유자 스레드로 돌려보낼 수 있게 해 줍니다. 이 인계는 reactor_drain_posts()가 전달하는데, 이 함수는 라운드당 한 번, 루프 맨 위에서만 호출되었습니다. 즉 *이전 CQE 묶음 전체*가 비워진 뒤입니다. 연결 512개짜리 묶음의 앞부분에서 끝난 백그라운드 작업은, 그 continuation 자체에는 느린 부분이 전혀 없는데도, 나머지 연결 511개의 핸들러가 모두 실행될 때까지 기다린 뒤에야 실행됩니다.

이는 이슈 #25가 실제로 보고하는 모양을 재현합니다. 평균은 평평한데 P99.999가 동시성에 따라 급격히 커지는 것입니다. 원인은 느린 요청이 아니라, 큰 묶음에 비해 운이 나쁜 *도착 시점*입니다.

수정

CWIST_REACTOR_DRAIN_CHUNK=<N>은 묶음 끝에서만이 아니라 연결 콜백 N개마다 reactor_drain_posts()를 끼워 넣습니다.

if (drain_chunk && ++since_drain >= drain_chunk && head != tail) {
since_drain = 0;
__atomic_store_n(reactor->impl.cq_head, head, __ATOMIC_RELEASE);
reactor_drain_posts(reactor);
}

0이면 이 부분을 완전히 건너뛰어 기존 동작으로 돌아갑니다. 루프는 수정 전과 똑같습니다. 설정하지 않으면 기본값은 64입니다. 이 수정은 외부 스레드의 post가 묶음의 나머지에 비해 언제 비워지는지만 바꿉니다. 처리되는 연결 수, 한 연결 안의 요청 순서, classic 풀 동작은 전혀 바꾸지 않습니다. 같은 검사가 세 디스패치 루프(io_uring, epoll, kqueue) 모두에서 실행되며, 위 스니펫은 io_uring 것으로, 거기의 head != tail 가드는 이벤트 배열 백엔드에서 i + 1 < n에 대응합니다. 그래서 묶음의 마지막 이벤트 뒤에는 쓸데없는 비우기가 따라오지 않습니다(라운드 맨 위의 비우기가 처리합니다).

측정된 효과

tests/bench_cooperative_queuing.c: 파이프 512개를 리액터에 들어가기 전에 모두 읽기 가능하게 만들고(그래서 512개 모두 한 비우기 라운드의 CQE가 됨), 각 콜백은 80us 핸들러를 흉내 냅니다. 백그라운드 스레드는 라운드 시작 200us 후에 cwist_reactor_post()를 한 번 보내고, 그 post에서 콜백까지의 지연을 측정합니다. 각 10회, 이 머신 기준:

설정 post에서 콜백까지 지연
기존 (설정 안 함) 41.1-41.4 ms (~= 512 x 80us, 즉 묶음 전체를 기다림)
CWIST_REACTOR_DRAIN_CHUNK=32 2.32 ms (~18배)
CWIST_REACTOR_DRAIN_CHUNK=8 0.38 ms (~107배)

epoll 백엔드 버전(bench_cooperative_queuing_epoll, 같은 소스에 CWIST_REACTOR_BACKEND=epoll을 박아 넣어 빌드)도 같은 모양을 보입니다. 변경 전 트리로 빌드한 baseline 바이너리와 교차 실행해 측정했습니다(라운드 5회 x 회당 10회 실행, 이 머신 기준). 기존 epoll 루프는 라운드 맨 위에서만 post를 비웠으므로 묶음 중간의 post는 이벤트 배열 512개 전체를 기다렸고, chunk=8은 그 대기를 약 8개 콜백으로 제한합니다.

설정 (epoll 백엔드) post에서 콜백까지 지연
baseline (변경 전, 묶음 중간 비우기 없음) 라운드당 평균 41.3-42.2 ms
CWIST_REACTOR_DRAIN_CHUNK=0 (새 코드에서 기존 동작) 평균 41.7 ms
CWIST_REACTOR_DRAIN_CHUNK=8 라운드당 평균 0.44-0.49 ms (~90배)

교차 실행하는 같은 바이너리 A/B(CWIST_REACTOR_DRAIN_CHUNK=0 대 8)는 CI의 .github/workflows/perf-epoll-drain.yml이 돌립니다.

tests/test_reactor_drain_chunk.c는 이 벤치마크의 통과/실패 버전으로 make test에 연결되어 있습니다. 청크를 쓴 post가 청크 없이 묶음 전체에 걸리는 시간의 절반 미만, 그리고 같은 실행에서 환경 변수를 설정하지 않았을 때 측정한 값의 절반 미만에 도착하는지 단언합니다.

비용 측면: 끼워 넣은 비우기 지점은 원자적 교환 한 번(MPSC 스택을 꺼내는 reactor_drain_posts, 큐가 비어 있으면 아무 일도 하지 않는 순회)과 청크 경계마다의 원자적 저장 한 번입니다. 연결 512개짜리 묶음에서 chunk=8이면 저렴한 원자 연산 64번이 더해지는데, 그 묶음에서 이미 약 41ms의 핸들러 작업이 쓰이고 있습니다. test_http_fairness와 test_reactor_wake는 모두 그대로 통과하며(테스트 실행에서는 기본적으로 환경 변수를 설정하지 않음), ASan+UBSan에서도 마찬가지입니다.

이 수정이 해결하지 않는 것

이 수정은 같은 묶음의 다른 연결에 비해 외부 스레드 continuation(cwist_async_defer, 백그라운드 작업 완료)의 대기만 줄입니다. cwist_async_defer를 전혀 쓰지 않는 평범한 동기 GET / 벤치마크에는 아무 효과가 없습니다. 그런 작업에는 끼워 넣을 외부 스레드 post가 없으므로, 이슈 #25에 이미 있는 the-benchmarker 방식의 수치가 이것만으로 움직이리라 기대하지 않습니다. 이것은 이슈가 추적해 온 디스패치 라운드 직렬화 계열 안의 실제적이고 별개인, 지금까지 다루지 않았던 빈틈이며, 묶음 안의 평범한 요청 꼬리 지연에 대한 추가 작업을 대신하지 않습니다 (그 작업에는 묶음당 인라인 작업 총량을 시간으로 제한하거나, 핸들러 실행을 리액터 스레드 밖으로 완전히 옮기는 것이 필요합니다. 둘 다 검토했지만 여기서 시도하지는 않았습니다. "전통적인 완료 큐" 인계가 평균 지연을 퇴행시킬 수 있다는 이슈 스레드의 경고를 보세요).

조정

헤더 직렬화와 응답 병합 작업(PR #180)이 반영된 뒤 기본값은 무조건 64로 설정됩니다. chunk=64에서 끼워 넣은 비우기는 연결 512개짜리 묶음당 최대 8번 일어나며, 이는 수십 밀리초의 핸들러 작업에 비해 적은 수의 저렴한 원자 연산입니다. CI가 실행하는 평범한 벤치마크 작업은 cwist_async_defer를 쓰지 않으므로 거기서는 이 경로가 실행되지 않습니다. 개선 효과는 실제로 백그라운드 작업이나 연기된 응답을 쓰는 배포에서만 보입니다.

묶음 중간의 비우기를 완전히 끄고 기존 동작으로 돌아가려면 CWIST_REACTOR_DRAIN_CHUNK=0으로 설정하세요. 더 작은 값(8-32)은 라운드당 원자 연산을 더 쓰는 대신 외부 스레드 post 지연을 더 줄입니다. 위 벤치마크에서 8은 최악의 대기를 약 41ms(묶음 전체)에서 약 0.38ms로 줄입니다.
