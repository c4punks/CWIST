Classic 풀의 버스트 기아 (#25 후속)

이것은 활성(liveness) 수리이며, 원래의 HTTP P99.999 보고가 해결되었다는 주장이 아닙니다. #37의 io_uring 깨우기 수리와도 독립적입니다.

원인과 변경

조건 변수에서 기다리는 워커는 깨어나 큐 뮤텍스를 다시 얻을 때까지 유휴 상태로 계산됩니다. 이전에는 idle_workers == 0일 때만 제출 과정에서 classic 풀을 키웠습니다. 그래서 신호를 받은 워커 하나가 아직 유휴로 계산되는 동안 버스트가 여러 연결을 큐에 넣을 수 있었습니다. 그 워커가 오래 사는 keep-alive 핸들러를 시작하고 나면, 남은 연결에는 워커도 없고 풀 증가를 일으킬 추가 제출도 없었습니다.

이제 제출은 큐 뮤텍스 아래에서 **대기 중인 수요와 유휴 용량을 비교**합니다. 최대 워커 수 검사와 스레드 예약도 같은 임계 구역에서 일어나므로, 동시에 제출하는 쪽들이 남은 같은 자리를 예약할 수 없습니다. 제출당 최대 한 번만 증가를 시도하며, 기존의 두 번 시도하는 스레드 생성 실패 롤백도 유지합니다.

풀 기본값, 공개 인터페이스, 리액터 백엔드, 할당자, 파이프라인 예산은 바뀌지 않습니다. 생성에 실패하면 여전히 기존 워커에게 작업이 남을 수 있으며, 자원이 고갈되고 기존 핸들러가 모두 블로킹된 상황에서의 진행을 약속하지는 않습니다. 기존의 분리된(detached) 워커 종료 동작은 이 수리의 범위 밖입니다.

결정론적 회귀 테스트

make WERROR=1 test_classic_pool_scaling은 별도 프로세스 네 개를 실행합니다.

  • 지연된 유휴 워커 하나와 붙잡힌 핸들러 여덟 개: 여덟 개 모두 어떤 핸들러도 끝나기 전에 시작해야 합니다. 예전 코드는 하나만 시작합니다.
  • 지연된 유휴 워커 세 개: 버스트는 여전히 동시 진입 여덟 개가 필요합니다.
  • 워커 상한이 4인 동시 제출: 상한을 넘지 않으며, 활성 핸들러 네 개가 풀려나면 작업 여덟 개가 모두 끝납니다.
  • 주입된 pthread_create 실패 두 번: 예약 하나가 롤백되고, 핸들러 일곱 개가 시작할 수 있으며, 풀려난 뒤 여덟 개 모두 끝납니다.

이 하네스는 프로덕션 큐 코드를 실행합니다. 조건 대기의 재획득을 지연시키고, 안전한 테스트 정리만을 위해 잡힌 워커 스레드를 join 가능하게 만듭니다. 프로덕션의 분리된 워커 종료를 테스트한다고 주장하지 않습니다. 이 테스트는 일반 make test 스위트에 포함되어 있습니다.

검증 상태

로컬 ARM64 Linux 환경에서 -Werror 빌드가 성공했습니다. make -k WERROR=1 test로 Makefile 테스트 대상 57개를 모두 실행한 결과 56개 통과, 1개 실패였습니다. 실패는 test_grpc.c:243의 append_grpc_string_frame 덧붙이기 단언이었습니다. 원래 dev HTTP 소스로 다시 빌드해도 같은 실패가 재현되었습니다. 이는 이 환경에서 관찰된 기존 실패이며, 근본 원인을 이해했다거나 전체 스위트가 통과한다는 주장이 아닙니다.

깨끗한 ASan/UBSan 빌드에서 누수 감지를 켜고 저장소의 기존 LSan 억제 파일을 사용해 다음 여섯 대상이 통과했습니다: test_classic_pool_scaling, test_http, test_http_pipeline, test_http_fairness, test_async_defer, test_conn_registry. 풀 모드 네 가지가 모두 통과했습니다. 독립적인 정적 검토에서도 막는 결함 후보는 발견되지 않았습니다. 호스팅 CI는 아직 검토해야 하며, 남은 검증 우려가 해소될 때까지 초안으로 둡니다.

HTTP 측정과 한계

로컬 측정에는 전용 ARM64 Linux VM(vCPU 4개, 4 GiB, 커널 6.8.0-117), 저장소의 고정된 빈 GET 벤치마크, classic 워커 프로세스 네 개, 부하 생성 스레드 두 개, FD 한도 65536을 사용했습니다. 측정한 각 20초 실행 앞에는 버리는 5초 워밍업이 있었습니다. 측정 시계를 바로잡은 뒤 64, 256, 512 연결에서 짝지은 세 라운드로 에러 없는 실행 18개를 얻었습니다. 양쪽 모두 #37이 적용되어 있었고, 이 패치는 그 리액터 깨우기 경로를 쓰지 않는 classic 풀만 바꿉니다.

wrk 4.2.0(a211dd5a7050b1f9e8a9870b95513060e72ac4a0)을 로컬에서 빌드했으며, time_us()가 gettimeofday 대신 clock_gettime(CLOCK_MONOTONIC)을 쓰도록 했습니다. 처음의 시스템 wrk 결과는 버렸습니다. Lima 시계 동기화 로그에 벽시계가 뒤로 가는 단계가 보였고, wrk의 부호 없는 지연 시간 뺄셈은 그것을 히스토그램 넘침 타임아웃으로 분류할 수 있기 때문입니다. 이는 측정 도구의 조정이지 서버 최적화가 아닙니다. wrk가 보고하는 백분위수에는 원시 관측값뿐 아니라 내장된 합성 지연 보정도 포함됩니다.

밀리초 단위 P99.999, 세 번의 실행 모두 (이전 -> 이후):

  • c64: 3.194, 3.185, 3.168 -> 5.576, 3.172, 3.160
  • c256: 3.707, 3.583, 3.573 -> 3.690, 3.623, 3.616
  • c512: 4.256, 4.172, 4.173 -> 4.276, 4.165, 4.266

일관된 정상 상태 P99.999 감소는 확인되지 않았습니다. c64 후보의 이상치는 숨기지 않고 남겨 두었습니다. 처리량 범위는 겹칩니다. 별도로 통제하지 않은 실제 HTTP 연결 버스트도 두 버전 모두에서 완료되었지만, 그 실행은 결정론적 테스트의 붙잡힌 워커 일정을 재현하지 않았습니다. 완료된 요청의 히스토그램만으로는 끝내 완료되지 않은 요청의 진행을 증명할 수 없습니다. 원래 이슈의 645.72 ms 결과는 이와 다른 하드웨어, 리비전, 작업 부하 설정에서 재현되지 않았습니다.
