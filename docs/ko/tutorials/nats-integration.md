# CWIST와 NATS 연동하기

CWIST에는 이벤트 기반 서비스를 위한 트리 내장 NATS 연동 지점이 있습니다. 비동기 작업과
팬아웃에는 NATS를 쓰고, HTTP 핸들러는 요청을 검증하고 제한된 시간 안에 응답을 돌려주는 역할만
맡기세요.

## 1. 요청과 워커의 책임 나누기

HTTP 핸들러는 JSON 명령을 검증하고, 요청 id를 부여하고, 다음과 같은 간결한 이벤트를 게시해야
합니다.

```json
{"type":"post.created","post_id":42,"request_id":"..."}
```

워커는 `blog.post.created`를 구독하고, 파생 작업을 저장하고, 결과나 실패 이벤트를 게시합니다.
주제(subject) 이름에는 소유자와 버전을 담으세요. 예: `blog.v1.post.created`.

## 2. 라우트에서 게시하기

NATS 클라이언트는 애플리케이션 시작 시 한 번 초기화하고, 요청마다 다시 연결하지 말고 오래 사는
연결을 공유하세요. 핸들러는 선택한 영속성 경계를 넘은 뒤에만 성공을 확인해야 합니다. 보내고 잊는
작업이라면 게시 성공이, 브로커 장애를 견뎌야 하는 작업이라면 데이터베이스 트랜잭션/아웃박스
기록이 그 경계입니다.

요청/응답에는 짧은 기한을 강제하고, 타임아웃이나 사용 불가 에러는
`503 Service Unavailable`로 바꾸세요. 기한 없는 NATS 구독에 HTTP 워커를 붙잡아 두지 마세요.

## 3. 신뢰성 점검 목록

- 소비자를 멱등하게 만드세요. 메시지는 재전달될 수 있습니다.
- 중복 제거와 추적을 위해 모든 이벤트에 메시지 id와 요청 id를 넣으세요.
- 게시하거나 소비하기 전에 페이로드 크기를 제한하고 스키마를 검증하세요.
- 워커가 재시작되어도 전달이 중요하다면 영속 JetStream 소비자를 쓰세요.
- 백오프를 두고 재연결하고, 연결 상태를 헬스 체크로 노출하세요.

NATS 메시지를 SSE나 WebTransport로 이어 줄 때도 같은 패턴이 적용됩니다. 전송 경계에서
직렬화하고, 백프레셔 한도를 유지하고, 명시적으로 중요하지 않은 실시간 갱신만 버리거나 합치세요.
