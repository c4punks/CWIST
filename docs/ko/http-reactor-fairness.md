# HTTP/1.1 파이프라인 공정성과 프레이밍

관련: [이슈 #25](https://github.com/c4punks/CWIST/issues/25).

## 범위

이벤트 기반 HTTP/1.1 핸들러는 호출당 **완성된 요청을 최대 16개**까지 처리합니다. 버퍼에 남은
요청은 핸들러를 재귀 호출하거나 다른 읽기 이벤트를 기다리는 대신, 리액터의 FIFO post 큐를 통해
이어서 처리됩니다. 이것은 경과 시간이 아니라 요청 디스패치 수를 제한합니다. 블로킹 핸들러, 큰
본문, 동기 파일 스트림 작업은 여전히 리액터를 점유할 수 있습니다.

논블로킹 파서의 예비 단계는 헤더 블록만 받습니다. 검증된 Content-Length/chunked 조립기가 그
뒤에 본문을 공급합니다. 이렇게 하면 이어지는 파이프라인 메시지를 본문 없는 요청에 복사하고, 긴
파이프라인의 요청마다 그 불필요한 복사를 반복하는 일을 피할 수 있습니다.

half-close는 continuation을 넘어서도 유지됩니다. 상대가 쓰기 쪽을 닫은 뒤에도 버퍼에 있는 완성된
요청에는 응답하며, 끝부분의 불완전한 요청은 영원히 재무장하지 않고 닫습니다. 풀 파괴 시에는
마지막 리액터 비우기에서 연기된 완료가 새 continuation을 만드는 것도 막습니다.

## 동작 회귀 테스트

```sh
make WERROR=1 test_http_pipeline test_http_fairness test_async_defer test_http_chunked
```

`test_http_pipeline`은 본문 없는 GET, Content-Length: 0, 양수 길이, chunked 프레이밍을 같은
버퍼에 다른 요청이 함께 있는 상태로 확인합니다.

`test_http_fairness`는 첫 파이프라인 핸들러에 관문을 걸고, 같은 리액터에서 두 번째 연결을 준비
상태로 만든 뒤 관문을 엽니다. 다음을 확인합니다.

- 대량 요청 256개가 모두 끝나기 전에 탐침 요청이 처리된다;
- 애플리케이션 핸들러 호출 한 번이 대량 요청을 16개 넘게 처리하지 않는다;
- 응답 프레임과 본문 256개가 추가 클라이언트 입력 없이 순서대로 모두 도착한다;
- 완성된 경우와 헤더가 잘린 half-close 변형에서도 유효한 요청을 비운다;
- 풀 파괴 중의 실제 연기된 완료가, 전역 실행 플래그가 참인 동안에도, 고아 continuation을 큐에
  넣지 않고 응답을 보낸 뒤 닫는다.

단언은 지연 시간 임계값이 아니라 처리 순서, 프레이밍, 수명 주기를 기준으로 합니다.
watchdog/poll 타임아웃은 고장 난 테스트가 멈추지 않게 할 뿐입니다. Makefile은 전체 스위트에서
이 변형들을 실행하고, macOS 집중 CI 작업은 두 새 테스트 대상을 명시적으로 실행합니다.

dev 기준선은 요청 **256/256**개가 끝난 뒤에야 탐침을 처리했고, 이후의 파이프라인 바이트를 GET
본문으로 노출했습니다. 처음의 공정성 구현은 수명 주기 회귀 두 가지(half-close 잘림, 마지막 파괴
비우기 안에서 만들어진 post)를 추가로 드러냈고, 둘 다 전용 회귀 테스트가 있습니다.

## 성능 주장의 경계

이 테스트들은 특정 head-of-line 블로킹 메커니즘이 제거되었음을 보여 줍니다. 원래 이슈의
645.72 ms P99.999가 해결되었음을 보여 주지는 **않습니다**.

저장소의 `GET /` 벤치마크 앱에 대한 별도의 폐쇄 루프 비교는 Linux x86_64, GCC 13.3, wrk 4.1.0,
프로세스/리액터 하나, 클라이언트 스레드 둘, 동시성 64/256/512, 워밍업 2초, 샘플 10초, 변형당 세
라운드를 사용했습니다. 유효한 실행 18개 모두 전송/상태 에러가 없었습니다. 처리량은 비슷했고,
극단 백분위수 지연은 일관되게 개선되지 않았습니다. 이 실험은 최종 정리 전용 가드가 들어가기 전의
공정성/프레이밍 후보를 사용했으며, 최종 릴리스 성능 수용 관문이 아닙니다.

이 결과만으로 #25를 닫지 마세요. 원래 벤치마크는 다른 부하 생성기를 씁니다. 일반적인 꼬리 지연
주장을 하기 전에 원래의 명령, 리비전, 워커 설정, 자원 한도, 호스트 조건을 재현하세요. P99.999에는
충분한 관측 수와 반복 실행도 필요합니다.

비교 가능한 로컬 실행을 위해서는 클라이언트와 서버를 시작하기 전에 **소프트** 디스크립터 한도를
(기존 하드 한도 안에서) 올리세요. 예: `ulimit -n 65536`. 소프트 한도 1024에서는 초기 진단
실행이 CWIST의 진행 중 요청 허용 한도에 걸려 503을 반환했고, 그 샘플은 지연 시간 개선으로 세지
않고 버렸습니다.

## 내부 API 호환성

`cwist_http_async_conn_t`를 할당하는 소비자는 끝에 추가된 `peer_eof` 필드 때문에 다시 빌드해야
합니다. `cwist_http_async_conn_fill()`은 이제 정상적인 EOF에 대해 0을 반환하고 그 필드에
기록합니다. 호출자는 버퍼에 있는 완성된 요청을 비운 뒤 닫습니다. 버퍼가 있는
`cwist_http_async_rearm()`은 작업을 인라인으로 실행하지 않고 예약합니다. 기존 실패 계약은 그대로
연결을 소비하고 닫습니다.
