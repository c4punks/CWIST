# C1M 파일 한도

이슈 #25에 대한 부분 수정입니다.

## 원인

기존 코드는 `setrlimit`을 호출하기 전에 두 파일 한도를 모두 1050000으로 설정합니다.
호출이 실패하면 두 번째 호출은 코드가 이미 바꿔 버린 값을 사용합니다.
그래서 코드는 원래 하드 한도 값을 잃어버립니다.

테스트 컨테이너에서 소프트 한도는 1024에 머물렀고, 하드 한도는 524288이었습니다.
낮은 소프트 한도 때문에 C1M 연결 한도도 낮았습니다.
프로세스 하나와 HTTP 워커 하나로, 열린 연결 40개 중 8개가 HTTP 503을 받았습니다.

## 변경

코드는 기존 하드 한도 안에서만 소프트 한도를 올립니다.
하드 한도를 바꾸거나, 이미 더 높은 소프트 한도를 낮추지 않습니다.
시스템 호출이 실패하면 성공 메시지가 아니라 에러 메시지를 출력합니다.

이 변경으로 테스트 컨테이너는 소프트 한도 524288을 사용했습니다.
40개 연결 모두 HTTP 200을 받았고, 하드 한도는 바뀌지 않았습니다.

## 조정

1050000이라는 목표값은 컴파일 시 기본값(`src/sys/app/app.c`의
`CWIST_DEFAULT_FD_LIMIT_TARGET`)이며, `CWIST_FD_LIMIT_TARGET`으로 덮어쓸 수 있습니다. 이런 종류의
조정값에 대한 프로젝트 관례(`CWIST_MALLOC_ARENA_MAX`, `CWIST_POOL_SHARDS`,
`CWIST_HTTP_YIELD_BATCH`, ...)와 같습니다. 기본값이 배포 환경에 맞지 않을 때 설정하세요. 예를
들어 컨테이너 할당량이 더 작거나, 연결당 fd를 둘 이상 여는 작업(프록시, 연결별 임시/로그
파일)인 경우입니다.

올바른 양의 정수가 아닌 값(설정 안 됨, 빈 값, 숫자가 아님, 뒤에 쓰레기 문자, 0, 음수)은 모두
기본값으로 돌아갑니다. `cwist_app_tune_system()`은 `target == 0`이나 일부만 파싱된 숫자로
실행되지 않습니다. 위의 하드 한도 제한과 이미 충분하면 아무것도 하지 않는 동작은, 목표값이
환경 변수에서 왔든 기본값에서 왔든 똑같이 적용됩니다.

```
CWIST_FD_LIMIT_TARGET=200000 ./your_cwist_app
```

## 검증

- 자식 프로세스 검사 세 개가 실제 파일 한도를 사용합니다.
- 시스템 호출 검사 여덟 개가 같은 값, 더 높은 값, 0, 무제한 값과 에러를 다룹니다.
- 테스트 검사는 `NDEBUG`에서도 활성 상태로 유지됩니다.
- ASan과 UBSan 검사가 자원 한도, HTTP, HTTP 파이프라이닝, 연기된 작업을 다룹니다.
- Linux ARM64 테스트 실행에서 Make 대상 59개 중 58개가 통과했습니다.
  `test_grpc`는 기준 커밋 `d08caace`와 이 변경 모두에서 `append_grpc_string_frame`에서
  실패했습니다.

이 변경은 이런 파일 한도에서 불필요한 HTTP 503 응답을 막습니다.
그것만으로 P99.999 지연 시간 개선을 증명하지는 않습니다.
